## 2. 失败分类与 checkpoint 实录

- **B 组 4×429 `MODEL_QUEUE_TIMEOUT`**(HTTP 429,`max_queue_ms≈10s`):老系统模型队列等槽超时,归环境失败,runner 重试后仍败 → 正确入 environment 台账,未污染内容失败。
- **D 组中断实录**:10 用例跑到 2 条完成时 Ctrl-C → checkpoint 恰 2 份落盘;同目录续跑自动补 8 条;其间 3 条环境失败(2×429 + 1×409,见 §4)→ 第二次续跑补成 **10/10**。manifest 校验(数据集 sha256/配置哈希)续跑全程未误拒。
- **内容失败 0**:链路稳定,无脚本错配类失败(错配风险已由题目侧排除说明覆盖)。

## 3. 并发 2 劣化幅度(定参输入,审查者预估 60-80% 的实测核对)

修正后对比(C vs A):
- 回合延迟:p50 **+67%**(7.0→11.6s),p95 **+98%**(8.8→17.3s);
- 墙钟:179.7s → 173.6s,**吞吐增益 ≈ -3%~0**(老系统模型队列实质串行化:tutor decode 并发 5,`max_queue_ms≈10s`,两个多回合流交叠即触顶);
- B 组教训:劣化不只是变慢——**队列顶死时 429 成批出现**,短退避(2-30s)救不回。

**定参结论**:`concurrency=2` + `env_retry_attempts=2` + `backoff_base_s=15 / cap_s=60`(C/D 组验证 5/5 与 10/10 全成)。基线夜跑建议维持并发 2(墙钟略优、失败有重试余量);并发 ≥4 在当前老系统容量下预期 429 成灾,不建议。上传化并发收益的前提是老系统扩模型队列/解码并发,那是环境侧决策。

## 4. 契约级发现(已修进适配器,单测覆盖)

1. **随机幂等键在续跑时不安全**:中断后被杀用例的服务端孤儿生成会继续落库;续跑若用新随机键重发同回合,服务端判并发更新 → **409 `SKILL_SESSION_CONFLICT`**("已被另一请求更新",流式 error 事件)。修复:幂等键从 case_id 稳定推导(`eval:{case_tag}:t{N}`),重发同键走服务端 message 级幂等(spike §2 实测),D 组第三次续跑 3/3 补成。注:此 409 是客户端可自愈的会话竞争,非题号歧义类环境 409,不触发停手红线。
2. **open 后不做冗余 refresh**:open 响应信封即新鲜状态;多一次刷新多占一次模型队列(B 组 429 的放大器)。spike 的 refresh 实测数字保留在结论文档,批跑路径不再调用。
